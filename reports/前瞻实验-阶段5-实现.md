## 1. Architecture

```text
strategy_v2 / S3 信号（按日期存档的 signals_<date>.parquet，只读）
        ↓
每日推荐：Top-K，剔除已持有 / 指数伪标的 / 板块受限，空缺席位等权
        ↓
T+1 限价挂单（限价 = entry_high，预留最坏情况现金）
        ↓
OPEN（target / stop / time_stop 在这一刻**锁定**）
        ↓
target / stop（盘中挂单，当日原子成交）｜ time-stop（收盘决策，次日开盘成交）
        ↓
CLOSED → 卖出资金当日可用
        ↓
下一轮

全程写入 append-only 账本；每次运行结束做现金对账，对不上就 raise，绝不自动改账。
```

**模块边界（`daily_exit_paper/`，9 个文件 / 2,329 行）**

| 模块 | 职责 |
|---|---|
| `config.py` | 配置读取 + **冻结校验**（自实现，不 import paper_live） |
| `store.py` | 目录布局、实验元数据、**不可变快照**、append-only 账本、原子写 |
| `state.py` | 订单 / 持仓 / 现金状态；**锁定字段白名单**；`PARTIAL_FILL_SUPPORTED=False` |
| `execution.py` | 市场数据（**每次访问都带 as_of**）+ T+1 可用性 + 限价/OHLC 判定 |
| `ledger.py` | 现金重算 + 结构恒等式 + 对账 |
| `decisions.py` | 人工干预三层（recommendation / decision / execution） |
| `engine.py` | 逐交易日事件循环（含追赶）+ 候选生成 + 推荐落盘 |
| `report.py` | 每日状态文本（**只格式化，不算钱**） |
| `__init__.py` | 包声明与隔离纪律 |

**一个刻意的设计：市场数据是注入的。** 引擎从不直接读 DB，而是走一个 `market`
对象（`LiveMarket` / 测试里的 `FakeMarket`）。整条状态机因此可以在毫秒级、
零副作用地跑完，且每个场景的数字都能直接对照。

**追赶（catch-up）**：若上次运行停在 s0、本次跑到 s1，s0 与 s1 之间的**每一个
交易日都会按同一顺序被逐个重放**。漏跑期间触发的止损不会被跳过。

## 4. State Machine

```text
PENDING_ENTRY ──成交──▶ OPEN ──target/stop──▶ CLOSED
      │                  │
      │                  └──time-stop──▶ PENDING_EXIT ──次日开盘──▶ CLOSED
      └──未成交/停牌──▶ NO_FILL（终态，不重试）
                                   任何状态 ──用户取消──▶ CANCELLED（终态）
```

| 状态 | 含义 | 终态 |
|---|---|---|
| `PENDING_ENTRY` | 限价单已挂出，等 T+1 判定 | 否 |
| `OPEN` | 已持仓 | 否 |
| `PENDING_EXIT` | 时间止损已触发，等下一个开盘 | 否 |
| `CLOSED` | 已平仓 | **是** |
| `NO_FILL` | 本次入场作废 | **是** |
| `CANCELLED` | 用户取消 | **是** |

`PENDING_EXIT` **只为时间止损存在**（详见 §6）。target / stop 是挂在市场上的
resting order，触发当天就能判定成交，所以内部原子完成，不引入无意义的状态。

## 5. Entry Model

| 规则 | 实现 |
|---|---|
| 限价 | `entry_high`（`trade_plan.plan.entry_band` 算出的区间上沿） |
| T+1 铁律 | 订单在 T 日收盘后产生，**只在 T+1 的 bar 上判定**；`signal_date > run_date` 直接拒绝 |
| 成交判定 | `open ≤ limit` → 成交 @ **open**（价格改善）；`open > limit` 且 `low ≤ limit` → 成交 @ limit；否则 NO_FILL |
| 停牌 | 执行日已在日历里、该股无 bar → **可判定的 NO_FILL**；日历里根本没有那一天 → 保持 `PENDING_ENTRY` |
| 部分成交 | **`PARTIAL_FILL_SUPPORTED = False`**，成交股数恒等于计划股数（0 或全量） |
| 股数 | 按**限价**反算最大手数，**含费用**且不超预算 |
| 阻塞 | 已持有的标的在退出前不再加仓 |

**价格改善必须记录**：`planned_entry_price` / `actual_entry_price` /
`entry_slippage` 三者都落进账本与日报。

## 6. Exit Model

| 出场 | 触发 | 成交价 |
|---|---|---|
| **target** | `high ≥ target` | `open ≥ target` → **open**（跳空越过）；否则 target |
| **stop** | `low ≤ stop` | `open ≤ stop` → **open**（跳空跌破）；否则 stop |
| **同日双触发** | 两条同时成立 | **一律按 stop**（`stop_first`，保守），并记 `both_hit_same_day` + `resolution_applied` |
| **time-stop** | 持有满 40 个交易日 | 收盘后判定 → **下一个交易日开盘**卖出 |
| **signal_exit** | — | **关闭**：排名跌出 Top-K 也不卖 |

**三条不许让步的规则（spec §18 / §50）**

1. **绝不用 close 冒充成交价**。`close` 是收盘才知道的，挂单不会等它。
2. **不猜盘中顺序**。日线不知道 target 与 stop 谁先到，交给配置里的保守策略。
3. **同日禁卖**。入场成交当天绝不卖出（A 股 T+1 制度），`s <= entry_exec_date` 直接跳过。

**时间止损的语义（写进测试）**：`entry_date` = 第 0 天；持有满 40 个**交易日**
触发；触发当天不成交，**下一个交易日开盘**卖出。为什么不用当天收盘价了结：
时间止损是收盘后才做得了的决策，当天收盘价是观察值，不是可成交价。

**target / stop 在入场成交时快照（§13）**：锚定在**实际成交价**上
（`target_and_stop(entry_px, entry_px, ...)`，复用既有公式，不重新发明），
同时把信号日的值存进 `at_signal` 仅作留痕。此后**永不修改** ——
`state.update_position` 对 18 个锁定字段直接 raise。

## 7. Cost Model

**唯一来源**：`personal_quant.strategy.costs.TransactionCostModel`。
配置里的 5 个费率与 `config/paper_live.yaml` **逐字相同**，并有测试断言这一点
（`test_cost_model_is_the_production_model`）—— 改一处就会红。

```text
entry_fee = buy_cost(value)     佣金 + 过户费 + 滑点
exit_fee  = sell_cost(value)    佣金 + 印花税 + 过户费 + 滑点
net_pnl   = (exit_value − exit_fee) − (entry_value + entry_fee)
```

滑点已含在 cost model 里，成交价不再另行加滑点（避免重复计费）。

**预估口径与账本口径一致性（§24）**：挂单时记 `estimated_value` /
`estimated_fee`，成交后与实际扣费逐笔比对。测试
`test_estimated_fee_matches_the_ledger_fee` 断言"成交在最坏情况（限价）时，
预估费与账本费逐分一致"。

## 8. Cash Accounting

| 量 | 定义 |
|---|---|
| `cash` | 账本余额（成交与费用都已入账） |
| `reserved_cash` | Σ 未成交买单的**预估资金占用**（限价 × 股数 + 预估费） |
| `available_cash` | `cash − reserved_cash` |
| `position_value` | Σ `shares × 收盘价`（拿不到就用最近一次标记价） |
| `portfolio_value` | `cash + position_value` |

**转移**：挂买单 → 预留（按限价，最坏情况）；成交 → 扣 `实际金额 + 费`、释放预留；
NO_FILL → 释放预留；卖出 → `cash += 卖出额 − 卖出费`（**当日可用**，A 股资金 T+0）。

**恒等式（全部有测试）**

```text
I1  cash ≥ 0                    I2  reserved_cash ≥ 0
I3  available_cash ≥ 0          I4  持仓股数 ≥ 0
I5  portfolio_value == cash + Σ shares×price
I6  Σ 账本现金流 == cash − initial_capital     ← 对账的核心
I7  完整周期后 portfolio_value == 初始本金 + 已实现盈亏
```

**对账失败 = raise，绝不自动改账**：`ReconciliationError` 会打印账本重算值与
state 记的值的差额，并要求人工核对。测试 `test_reconcile_raises_on_a_tampered_state`
直接篡改 state 验证这一点。

**落盘顺序**：**先写 state、再写账本**。state 是进度标记；万一崩在中间，账本会
落在后面 → 下次运行对账大声报错，而**不会重放同一段交易日导致整段被记两遍**。

## 9. Manual Override

三层独立保存，**绝不互相覆盖**：

| 层 | 文件 | 谁写 |
|---|---|---|
| ① 系统建议 | `recommendations/<signal_date>.json` | 引擎写，**写后只读** |
| ② 用户决定 | `decisions/<signal_date>.json` | 人写（`ADOPT` / `SKIP` / `MODIFY`） |
| ③ 实际执行 | `executions/<signal_date>.json` | 人回填 |

- **缺省 = 全部采纳**（不产生文件 ⇒ "被干预过"本身就是可检索的信号）。
- `SKIP` / `MODIFY` **必须写 `override_reason`**，否则拒绝写入。
- **用户的修改不写回 ①**：测试 `test_modify_applies_the_users_price_and_quantity`
  断言用户把限价改低之后，`recommendations/` 里仍然是引擎当时给出的那一份 ——
  所以"如果完全照系统做会怎样"这个问题永远可回答。
- 干预统计（`override_summary`）**只用于事后解释，绝不用来自动调参**。
- 跨日干预记录每天在日报的 `MANUAL OVERRIDES` 段落里展示。

## 10. Idempotency

| 动作 | 结果 |
|---|---|
| 同一天运行两次 | `state.as_of` 已推进 ⇒ 无交易日要处理 ⇒ **noop**，state 与账本一字不改 |
| 同一天重跑（成交后） | 同上：**零重复成交、零重复费用、零重复现金变动** |
| 推荐快照重复写 | 内容相同 → 无操作；内容不同 → `AlreadyWritten`（不可变铁律） |
| 回退到更早的日期 | **拒绝**（"实验时间只能向前"） |
| 未来日期 | **拒绝**（"还没有行情"） |
| `--dry-run` | 算出全部内容但**零写入**（state / 账本 / 快照都不产生） |

`created_at` 是墙钟时间、不参与"内容有没有变"的比较 —— 否则同一天用同样输入
重跑会撞上不可变铁律。

## 13. Integration Tests

按 spec §41 手工构造的完整场景（合成行情，逐日推进）：

```text
DAY 0  生成 BUY A（限价 = entry_high）
DAY 1  A 开盘低于限价 → FILLED @ 开盘价（价格改善），target / stop 锁定
DAY 2  价格在区间内 → HOLD
DAY 3  high 打到 target → SELL @ target，当晚资金入账并生成 BUY B
DAY 4  B 全天未触及限价 → NO_FILL，预留释放
DAY 5  账户回到全现金，无新信号 → 不建单
```

整条链在账本里**完整可追溯**：

```text
ORDER_CREATED → CASH_RESERVE → ORDER_FILLED → CASH_RELEASE
              → POSITION_OPENED → FEE
              → POSITION_CLOSED → FEE → ORDER_NO_FILL → RUN_SUMMARY
```

`POSITION_OPENED.entry_exec_date == D1`、`POSITION_CLOSED.run_date == D3` ——
信号、下单、成交、持仓、出场、现金、账本每一环都有日期。

## 14. Synthetic Scenario Results

| 场景 | 结果 |
|---|---|
| 限价未触及 | NO_FILL（终态），账户一分钱未动，预留全额释放 |
| 开盘优于限价 | 按**开盘价**成交（不是限价），滑点为负，如实记录 |
| 盘中触及限价 | 按限价成交 |
| 执行日停牌 | NO_FILL，原因写明"无有效 bar" |

| 止损成交 | @ stop；`open ≤ stop` 时 @ open |

| 时间止损 | 第 40 个后续交易日触发（入场日 = 第 0 天），次日开盘成交 |

## 15. Remaining Risks

| # | 风险 | 说明 |
|---|---|---|
| R1 | **缓存不按 symbol 筛选** | PHASE 4 遗留（§12 R1）。本实验不读特征缓存（信号走按日期存档的快照），但共享的 `compute_features` 仍有此性质 |

| R3 | **时间止损的次日开盘成交** | 是刻意的保守建模（§6）。若日后接入分钟数据可做更精确的模型，但必须新开版本 |

| R5 | **未接 nightly** | 按 §39 刻意不接。PHASE 5 是 standalone；接入要另开 integration 阶段 |
| R6 | `decisions/` / `executions/` 只有函数入口，没有 CLI 子命令 | 用户手写 JSON 即可（schema 见 `decisions.py` docstring 与 §9）。若嫌麻烦可后续加 `--decide` 子命令 |
| R7 | 未在真实数据上跑过多日连续场景 | 只做过 `--dry-run` 与首次建单的验证；真实多日运行留给 PHASE 7 |

## 16. How to Run

# 前置：当天数据与信号已刷新（nightly 的老流程）

### 两件必须让你知道的事

**① 我清除了一次验证运行产生的实验目录。**

为了验证 CLI 端到端能跑，我在真实数据上执行过一次
`run_daily_exit_paper.py --capital 66000`（非 dry-run），它在
`experiments/daily_exit_paper_v1/` 下产生了 `experiment.json` / `state.json` /
`ledger.jsonl`（41 条事件）/ `recommendations/2026-09-29.json` / `daily/`。

按你的规划，**真正的 forward 实验从 PHASE 7 才开始**，而且那一次运行会：
(a) 把本金永久锁定成 66,000（你就不能换本金了）；
(b) 拿 **09-29 的信号**挂单、执行日落在已经过去的 09-30 开盘上。

所以我**把那个目录删掉了**（该目录是我几分钟前刚创建的，不是你的既有数据），
把"起跑"这个决定留给你。真实数据上的行为已经由 `--dry-run` 验证过：
同一份信号、同样的 20 笔挂单、同样的对账结果 —— dry-run 不落盘。

**② 默认参数下会大量闲置现金。**

6.6 万本金 / 20 个等权空位 ≈ 3,135 元/位，很多高价股连 1 手都买不起，

（`trade_plan` 里的 `suggest_top_k` 就是为解决这件事存在的，但那是账户口径的
UX 特性，不是本实验的冻结参数）。若你希望更集中，需要**新开版本**
（`daily_exit_paper_v1.1`），因为那等于改仓位规模。
