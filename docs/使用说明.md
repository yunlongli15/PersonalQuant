## 1. 五分钟上手

本系统有**两个前端**，共用同一套引擎、同一份交易计划，数字必然一致
（都读 `data/quant/trade_plans/trade_plan_<信号日>.json`）：

| 前端 | 启动 | 地址 | 用途 |
|---|---|---|---|
| **录入界面**（本指南默认） | `python scripts/webapp/serve.py` | http://127.0.0.1:8765 | **日常就用它**：每日录入、交易计划、流水、收益 |
| **研究终端** | `python scripts/run_app.py` | http://127.0.0.1:8501 | 回测/因子/新闻/风险/模拟盘等 12 个研究页面 |

```bash
# 日常（每次使用）
source .venv/Scripts/activate
python scripts/webapp/serve.py
# 浏览器打开 http://127.0.0.1:8765
```

界面只在**本机**运行（绑定 127.0.0.1），财富数据不出本机。
**两个界面不能同时开**：DuckDB 单进程独占，同开会让数据刷新失败
（关掉界面再跑命令行任务）。

> **日期怎么读**：页面上的 `信号日` 是"**数据截至哪一天**"，不是"今天"。
> 上游行情发布有滞后（通常 1~2 天），所以信号日常常是上一两个交易日。
> 交易计划页同时显示 `生成于`（这次是什么时候算的），两者都对才说明是新的。

**第一次使用**（只做一次）：

```bash
python scripts/wealth/init_wealth_db.py      # 建财富库（含默认平台）
# 在 GUI「Daily Update」录入今天的资产，或先用下面的 Demo：
python scripts/quant/run_full_loop.py --demo-wealth
```

### 每天运行：**两条命令，先 A 后 B**（本节是唯一权威说法）

| | **A. `python scripts/quant/refresh_all.py`** | **B. `python scripts/run_daily.py`** |
|---|---|---|
| **职责** | 更新**数据与信号** | **记账与观察** |
| 具体做什么 | 行情快照、新闻、估值、因子缓存、全市场信号、当天实时价、预测、**交易计划** | 数据健康检查、Paper Live 前瞻记录、个人账户快照、收益 / 风险、冻结校验、告警、**日报** |
| 耗时 | 5~7 分钟（上游有新行情时再加下载约 5 分钟） | 约 5 秒 |
| 产出给谁看 | 界面「交易计划」「今日信号」「价格预测」 | 界面顶部状态条、`reports/daily/<日期>.md`、forward holdout 记录 |
| 会推进「信号日」吗 | **会** —— 只有它会下载新行情 | **不会** —— 它只读现有数据 |

```bash
python scripts/quant/refresh_all.py   # ① 先更新数据与信号
python scripts/run_daily.py           # ② 再跑每日流水线
# 然后在 GUI「Daily Update」输入今天的金额
```

**顺序不能反。** `run_daily.py` 不下载行情，它的"今天"来自本地已有数据；
先跑 B 的话它会对着**旧的一天**做记录（这就是之前"怎么还是 18 日"的原因）。
等 A 把数据推进后，B 才会记录到新的一天。

**只跑一条会怎样**：

- **只跑 A**：数据和交易计划是新的，但没有日报、没有 forward holdout 记录、没有告警。
- **只跑 B**：日报和前瞻记录会一直停在旧的一天，并且 `market_data` 步骤会报
  `WARNING：上游已有 X —— 有新数据未下载`，提示你去跑 A。

**两条都不要在开着界面时跑**：DuckDB 单进程独占。

`refresh_all.py` 会逐个作业打印进度（`[3/10] news_update ... 运行中`），
共 10 个作业：行情 → 复权因子修复 → 公告 → 新闻事件层 → 估值 → 因子缓存
→ 信号 → 实时价 → 预测 → 交易计划。
**不会静默卡住**。上游有新数据时才需要下载行情快照（约 566 MB；没有新数据
会自动跳过，不会白下）。

**`financial_update` 默认不跑**：财报全量抓取实测**要 2 小时以上**，
而生产特征集不含财务因子。需要时显式：

```bash
python scripts/quant/refresh_all.py --only financial_update
```

中途按 Ctrl-C 中断是安全的：不会写坏数据，下次运行会把中断的作业
标记为 `INTERRUPTED` 并重新跑。

## 2. 每日操作流程

| 步骤 | 在哪做 | 说明 |
|---|---|---|
| 1. 刷新数据与信号 | 命令行 `python scripts/quant/refresh_all.py` | 市场/新闻/估值/因子/信号/实时价/预测/交易计划 |
| 2. 跑每日流水线 | 命令行 `python scripts/run_daily.py` | 前瞻记录 + 日报 + 告警（几秒） |
| 3. 录入资产 | GUI → **Daily Update** | 只填"今日金额"，收益自动算 |
| 4. 看推荐 | GUI → **Trade Plan** | 明日买卖清单（见第 6 节） |
| 5. 执行后回填 | GUI → **Transactions** | 真实成交价/股数/费用 |
| 6. 月末复盘 | GUI → **Performance** | 收益归因：多少来自本金、多少来自投资 |

### ⚠️ 有资金进出时，要做**两件事**

「流水」和「金额」是两回事，系统**不会替你推算余额**：

| | 记录什么 | 在哪 |
|---|---|---|
| **流水**（transactions） | 那天**发生了什么**：转入/转出/买卖/分红 | GUI → Transactions |
| **金额**（snapshots） | 那天**账户里有多少钱** | GUI → Daily Update |

所以转入/转出（含**产品之间互转**）之后：

1. 先在 **Transactions** 记一笔（不记的话，转出会被当成亏损）
2. **再回到 Daily Update 填今天的金额** —— 这一步不做，资产总览和持仓
   就不会变，因为系统只认你填的金额

Daily Update 页面上会列出"上次录入之后还没反映到金额里"的流水，
照着平台 App 上的实际数字填即可。

> 为什么系统不自动改金额？因为转账可能还没到账，基金还有市场波动 ——
> 自动推算出来的数字**不是事实**，本系统宁可让你填。

## 4. 关键指标定义

### 财富侧

| 指标 | 定义 |
|---|---|
| **净资产** | 所有产品最新市值之和（现金类按金额） |
| **投资盈亏 P&L** | `期末 − 期初 − 外部净流入`。**转入转出不算收益** |
| **外部资金流** | 只有 转入/转出/存入/取出 是外部流；买卖、申赎是内部流 |
| **TWR** | 时间加权收益率：剔除资金进出时点影响的"选股能力" |
| **XIRR** | 资金加权收益率（年化内部收益率）：考虑每笔钱投了多久 |
| **万份收益** | 货币基金口径：每 1 万份当日的收益（元）。年化 = 万份收益 ÷ 10000 × 365 |
| **已实现/未实现盈亏** | 已卖出落袋 / 仍持有的浮盈浮亏 |

> **为什么不能"今日资产 − 昨日资产"当收益？**
> 今天转入 5,000 元，资产从 10,000 变 15,000，差额是**本金**不是收益。
> 系统一律扣除外部资金流后再算收益。

### 量化侧

| 指标 | 定义 |
|---|---|
| **信号分（prediction）** | 冻结模型对"未来 20 日相对收益"的排序分数，**只有相对大小有意义** |
| **raw_rank** | 该股票在全部标的中的排名（模型原始顺序，系统绝不改动） |
| **预期收益** | 该分数分桶下、历史上未来 N 日的平均收益（**模型估计，不是承诺**） |
| **P(上涨)** | 该分桶历史上涨概率 |
| **5–95% 区间** | 该分桶历史收益的 5% 与 95% 分位（多数情况会落在其中） |
| **预期波动** | 组合年化波动率（基于过去 60 个交易日协方差） |
| **换手率** | 单边口径：`0.5 × Σ|新权重 − 旧权重|` |
| **IR（信息比率）** | 相对基准的超额收益 / 跟踪误差 |

## 5. 板块交易权限（重要）

A 股不同板块有**开通门槛**，达不到就**买不了**：

| 板块 | 代码特征 | 门槛（20 个交易日日均资产） | 交易经验 |
|---|---|---|---|
| **主板** | 600/601/603/605.SH、000/001/002/003.SZ | 无 | 无 |
| **创业板** | 300xxx.SZ、301xxx.SZ | **10 万元** | 24 个月 |
| **科创板** | **688xxx.SH** | **50 万元** | 24 个月 |
| **北交所** | 4xxxxx / 8xxxxx / 920xxx | **50 万元** | 24 个月 |
| ETF/基金 | 51/56/58.SH、15/16/18.SZ | 无 | 无 |

### 系统怎么处理

1. **交易计划默认排除买不了的板块**（`exclude_restricted=true`）：
   先剔除受限标的，再从前 K 名中选股，资金不会被"买了也买不到"的标的占用。
2. 被排除的标的会在计划里单列（`excluded_restricted`），**不隐藏**，
   你可以看到"因为没到 50 万，错过了哪些票"。
3. 计划表格里的 `board_name` 列标明每只股票的板块，
   `can_buy` 列标明当前是否能买。
4. **临界提示**：资金刚好过线（如 10.0 万 vs 创业板 10 万门槛）时，
   会标注"临界达标，需按 20 日均资产在券商核实"——因为门槛算的是
   20 个交易日**日均**资产，不是某一天余额。
5. **交易经验**未核实时给提示而非禁止（你可能早就开通了）；
   在 `config/account_profile.yaml` 填 `experience_months` 后即严格判断。

### 账户档案配置

```yaml
# config/account_profile.yaml
account:
  capital: 100000            # 可投资金（元）
  auto_detect_capital: true  # 与财富库净资产取较大值
  experience_months: null    # 交易经验月数；null = 未核实（只提示）
```

## 6. 交易计划怎么看

### 表头逐列解释

| 列 | 含义 |
|---|---|
| `symbol` / `name` | 代码 / 名称 |
| `board_name` | 板块（主板/创业板/科创板/北交所） |
| `raw_rank` | 模型排名（1 = 模型最看好） |
| `current_price` | 最新收盘价 |
| **`recommended_entry_price`** | **计划买入价**（不是"现价买入"） |
| **`entry_low`–`entry_high`** | **可接受买入区间**：区间内成交都算合格 |
| `shares` | 建议股数（A 股 100 股整数倍） |
| `buy_value` | 买入金额 |
| `target_price` | 目标价（模型估计，**不是保证**） |
| `stop_loss` | 止损价 |
| `expected_return` | 预期毛收益（20 日） |

### ⚠️ 先看价格的日期

计划和报告里有两个日期，**别把它们当成一个**：

| 日期 | 是什么 | 会不会变旧 |
|---|---|---|
| **信号日**（`as_of`） | 模型打分的日期 = 数据截至哪一天 | 上游没发新数据就一直是它，**不是过期** |
| **价格日期** | 现价/入场区间用的是哪天的收盘 | **会过期** —— 价格每天都在动 |

`refresh_all.py` 里的 `live_price_refresh` 会抓**当天真实收盘价**覆盖价格
（排序仍停在信号日），所以正常情况下价格日期就是今天。

如果抓不到当天价格（休市、断网），报告会显式警告：
`⚠ 价格是 X 的收盘价（N 天前），入场区间可能已经失效`。
**看到这行就别照着入场区间挂单了** —— 先跑
`python scripts/quant/refresh_live_prices.py` 再重新生成计划。
| `expected_net_return` | **扣掉双边交易成本后的净收益** |

### 买入价是怎么定的

```
1. 取个股过去 20 日"日均绝对涨跌幅"作为波动度量
2. 区间半宽 = 波动 × 风险档系数，上限 3%
     保守 0.6×   平衡 1.0×   激进 1.4×
3. 计划价 = 区间中点
4. 资金按"计划价 + 交易成本"计算股数，
   这样即使成交在区间上沿也不会超预算
```

### 卖出依据（系统会给原因，不只给"卖"）

1. 达到目标价 2. 信号排名跌出前 K 3. 止损 4. 时间止损
（持有超过 2 倍预测周期） 5. 风险约束触发 6. 组合调仓

### 资金适配（小账户必读）

- 100 股是最小交易单位。账户 10 万元、持仓 20 只时，每只只有 4,750 元，
  **很多 50 元以上的股票连 1 手都买不起** → 资金大量闲置。
- 系统按**纯资金/手数算术**（不看任何收益数字）自动挑选持仓数 K：
  在「持仓 ≥ 5 只」且「投入 ≥ 60%」的前提下取最大 K，通常落在 **6–10 只**。
- 计划里 `shares = 0` 的行是"买不起 1 手"，不是系统故障。
- 想提高投入率：增加本金，或接受更少的持仓数（更集中）。

## 7. 数据状态与刷新

### Data Status 面板

| 状态 | 含义 |
|---|---|
| ✓ OK | 数据已是最新 |
| ⚠ **DATA STALE** | **数据过期**——推荐可能基于旧数据，先刷新 |
| ✗ missing | 该数据域缺失 |
| — not computed | 还没算过（如 Forecast 未生成） |

**为什么会出现 STALE**：上游数据源本身有延迟（官方公告索引滞后约 5 天、
行情快照按交易日更新）。系统如实显示，**不会假装数据是新的**。

### 刷新

```bash
python scripts/quant/refresh_all.py --status    # 只看状态
python scripts/quant/refresh_all.py             # 全部刷新（需要网络）
python scripts/quant/refresh_all.py --only signal_refresh,forecast_refresh
PQ_MODE=offline python scripts/quant/refresh_all.py   # 离线（网络任务记 SKIPPED）
python scripts/quant/update_market_snapshot.py --check  # 查上游有无新快照
```

**离线时网络任务记为 SKIPPED，绝不记为成功**——这样"没刷新"永远不会
被误当成"刷新过了"。

## 8. 常见问题

**Q：为什么推荐的股票 `shares = 0`？**
A：目标金额买不起 1 手（100 股）。高价股在小账户上很常见，见第 6 节。

**Q：为什么计划里没有某只高分股票？**
A：可能被板块权限排除（科创板需 50 万），或被指数伪标的过滤，
或在 Top-K 之外。`excluded_restricted` 字段能看到被权限排除的名单。

**Q：今天的收益怎么是 0？**
A：只有一天数据时没有"日收益"可比。录入第二天后开始有日盈亏。

**Q：转入 5 万后收益率反而降了？**
A：这是设计目标之一。系统扣除外部资金流再算收益，转入本金不会
被算成收益，也不会稀释收益率（见第 4 节 P&L 定义）。

**Q：能自动下单吗？**
A：**不能，也永远不会**。系统只输出建议，下单由你在券商 APP 手动完成。

**Q：数据要上传到云吗？**
A：不。除下载行情/公告外没有任何对外请求；GUI 只绑定本机；
`config/.env` 里的 API key 不进 git、不进日志。

**Q：怎么备份？**
A：GUI → Settings → "Back up wealth database"（生成
`backup/wealth_YYYYMMDD_HHMMSS.db`），或
`python scripts/wealth/init_wealth_db.py --backup`。

## 9. 本系统的边界（务必阅读）

1. **不是投资建议**。系统输出的是模型在历史数据上的统计结论，
   不预测未来，不保证收益。
2. **研究候选状态**。strategy_v2 的 candidate gates 为 7/9，
   未全部通过，**保持研究候选，不是生产策略**（原因见
   `reports/步骤6-最终候选.md`）。
3. **组合优化没有带来增量**。STEP 6 结论：等权已足够好，
   没有任何优化器在 research+valid 上超过等权（如实记录）。
4. **数据有延迟**。行情按交易日更新，公告索引滞后约 5 天；
   Data Status 会如实标注。
5. **新闻 LLM 层未启用**（无 API key），当前为纯规则版；
   结果不会被写成"LLM 结论"。
6. **回测≠实盘**。回测含理想化假设（T+1 开盘整单成交、
   未建模冲击成本）；实盘会有滑点与流动性差异。
7. **永远自己决策**。系统给区间、给理由、给风险边界，
   最终是否买卖由你判断并承担后果。

## 10. daily_exit_paper_v1 前瞻实验

> **状态：已就绪，尚未启动。** 启动需要两个只有你能给的东西：
> **初始本金** 与 **正式起始日**。系统不会替你选。

### 它是什么

一套**独立于** monthly paper_live 的前瞻模拟实验，用来在真实市场里检验
「S3 信号 + 有明确出场规则」的组合：

```text
strategy_v2 / S3 信号（冻结，只读）
   → 每日推荐（Top-K=20，空缺席位等权）
   → T+1 限价入场（限价 = 可接受区间上沿）
   → 持仓：target / stop / time-stop（40 个交易日）
   → 平仓 → 现金回流 → 下一轮
```

**它与 monthly paper_live 完全独立**：不同的目录、不同的账本、不同的执行语义，
互不读写。也**不读**你的财富库或任何人工交易记录。

### 怎么运行

```bash
source .venv/Scripts/activate

# 每天的固定三步（第三步只在你确认后执行）
python scripts/quant/refresh_all.py            # ① 更新数据与信号
python scripts/run_daily.py                    # ② 每日流水线
python scripts/quant/run_daily_exit_paper.py   # ③ 推进实验（几秒）

# 只看不改
python scripts/quant/run_daily_exit_paper.py --dry-run     # 空跑，磁盘零变化
python scripts/quant/run_daily_exit_paper.py --preflight   # 只做上线前检查
python scripts/quant/run_daily_exit_paper.py --show-state  # 只看当前状态
python scripts/quant/run_daily_exit_paper.py --reconcile   # 只对账
```

**首次启动**（只做一次，本金一旦写入就永久锁定）：

```bash
python scripts/quant/run_daily_exit_paper.py --capital <你的本金>
```

### 它保证什么（这些都有测试锁死）

| 保证 | 含义 |
|---|---|
| **T+1** | T 日收盘出信号，T+1 开盘才可能成交。绝不当天买 |
| **限价入场** | 开盘价低于限价 → 按**开盘价**成交（价格改善）；全天高于限价 → 不成交（终态，不追） |
| **目标/止损锁定** | 入场成交时按**实际成交价**锚定并**冻结**。之后再生成推荐也**改不动**它 |
| **同日不卖** | 当天买入的股票当天不能卖（A 股 T+1 制度） |
| **跳空保守** | 开盘跳过目标价/止损价 → 一律按**开盘价**成交，不假装能按挂单价成交 |
| **同日双触发** | 日线不知道盘中先后 → **一律按止损**（保守） |
| **绝不用收盘价成交** | 收盘价是收盘才知道的，挂单不会等它 |
| **对账失败即报错** | 现金与账本对不上就停下来，**绝不自动改账** |
| **不可变快照** | 每天的推荐写一次就不再改，连你自己也覆盖不了 |

### 人工干预（可选）

缺省 = **完全采纳系统建议**。想改的话，在
`experiments/daily_exit_paper_v1/decisions/<信号日>.json` 写：

```json
{"signal_date": "2026-10-08", "default_action": "ADOPT_ALL",
 "decisions": [{"symbol": "601086.SH", "action": "SKIP",
                "override_reason": "不想买这只"},
               {"symbol": "601998.SH", "action": "MODIFY",
                "limit_price": 9.00, "quantity": 300,
                "override_reason": "挂低一点"}]}
```

- `action` 只能是 `ADOPT` / `SKIP` / `MODIFY`；
- `SKIP` 和 `MODIFY` **必须写 `override_reason`**；
- **你的修改不会写回系统建议** —— 所以"如果完全照系统做会怎样"永远可回答。
- 实际成交回填到 `executions/<信号日>.json`（三层分开存）。

### 每天产出什么

- 终端：`DAILY EXIT PAPER` 报告（三个时间、组合、持仓、挂单、成交、费用、对账）
- 文件：`reports/daily_exit_paper_v1/daily_<日期>.md`
- 账本：`experiments/daily_exit_paper_v1/ledger.jsonl`（append-only）

### 规矩（很重要）

1. **代码冻结**。实验开始后，除非发现真实 bug，**不改任何交易规则**：
   不改 Top-K、不改 horizon、不改 target/stop、不改仓位规模、不改成本模型。
2. **禁止短期调参**。连续止损 5 笔不改规则，连续盈利 5 笔也不加仓位。
   规则固定、市场真实变化、观察结果 —— 这才是实验的意义。
3. **改规则 = 新建版本**（`daily_exit_paper_v1.1`），新目录、新账本；
   绝不改完继续叫 v1。
4. **不删记录**。错误也必须保留。已经影响成交/现金/持仓的 bug →
   **停止实验**先审计，不得手工改 ledger。
5. 任何 bug / 人工干预 / 数据中断 / 漏跑 / 异常成交都记到
   `experiments/daily_exit_paper_v1/incidents.md`。

### 关于"每天要盯盘吗"

不用。`run_daily_exit_paper.py` 几秒钟跑完，会告诉你：昨天挂的单成交了没有、
持仓有没有触发目标价/止损、今晚要挂什么单。你只需要在下单时打开券商 APP。
